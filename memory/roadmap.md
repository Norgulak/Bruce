## AI & Intelligence — Feature Priority (set 2026-08-13, Banmi wants "important features" prioritized over process/fixes)

**Phase 1 — build out Bruce's full component set:**
1. Persistent memory for Bruce himself (not just this project vault — Bruce-the-assistant having his own long-term memory of Banmi: facts, preferences, history) — inspired by reel 4 (alex2learn) and reel 7 (raycfu), same pattern already proven in this vault. **[DONE 2026-08-14 — merged to `main`. Both explicit ("remember that X") and passive (automatic extraction on session end) paths hardware-verified across a full Bruce restart. See decisions-log for the full build/review/fix history.]**
2. Smarter locally hosted model — bigger Qwen model or Mistral. Low effort relative to payoff. **[DONE 2026-08-17, hardware-verified]** Switched `OLLAMA_MODEL` from `qwen2.5:7b` to `qwen3-14b-iq4xs`. First tried the standard `qwen3:14b` (Q4_K_M, 9GB) via `ollama pull`, which kept hitting a network issue (see below) and, once finally loaded via manual import, turned out too large to fit fully in VRAM alongside Whisper — confirmed via Ollama's own logs showing generation crawling at 4.67-7.05 tokens/sec (vs. an expected ~54 tok/s), a clear sign of CPU spillover. Re-downloaded as `IQ4_XS` (8.14GB, a more memory-efficient quantization that keeps quality close to Q4_K_M) via manual browser download + `ollama create` import — confirmed via hardware test to run fully on GPU (no 99% GPU spike, no CPU spillover, 3-8s response times). Original plan was `gpt-oss:20b` (OpenAI's Apache-2.0 open-weight MoE model) — abandoned after two real findings: (1) Bruce's actual GPU is an **RTX 5070, not a 5070 Ti** as this vault had recorded everywhere — 11.9 GiB total VRAM / ~10.8 GiB available per Ollama, not 16GB. gpt-oss:20b needs ~12.4GB just for weights (MoE saves compute, not memory — all experts still have to be resident in VRAM), so it flatly doesn't fit, and would force slow CPU/RAM offload that reintroduces the response-delay problem Pocket TTS just fixed. (2) Independently, the `gpt-oss` download itself repeatedly stalled/reverted on Banmi's machine — root cause found via `%LOCALAPPDATA%\Ollama\server.log`: Ollama pulls in 16 parallel connection streams by default (a known Windows issue, see `OLLAMA_MAX_TRANSFER_STREAMS`), which kept stalling all at once. `OLLAMA_MAX_TRANSFER_STREAMS=1` is now set on Banmi's machine via `setx` — worth keeping for any future large pulls even though we ended up not needing it for `qwen3:14b`. **Standing principle for future model choices, per Banmi 2026-08-16: pick the smartest model that fits without performance compromises — do not trade response speed for capability.**
   - **Future idea, hardware-gated, not started**: revisit `gpt-oss:20b` (or similar) if Banmi adds another GPU. Important caveat already checked: his other spare cards are AMD, and Ollama currently does **not** pool VRAM across mixed NVIDIA+AMD GPUs — in a mixed setup the AMD card just sits idle. This path would need either a second NVIDIA GPU or a single larger NVIDIA GPU replacing the 5070, not an AMD card added alongside it. **[proposed, 2026-08-16]**
3. Streaming TTS to fix the ~5s response delay. Also listed under Pending Fixes — same underlying problem. **[DONE 2026-08-14 — pending merge]** `kyutai-labs/pocket-tts` integrated into `bruce.py` on branch `bruce-pocket-tts` (real streaming via `generate_audio_stream()`, not the blocking `generate_audio()` — first version had a 5-10s delay, fixed). Banmi hardware-tested and preferred it over every other voice tried, and it's now set as the **default voice** (falls back to Kokoro gracefully if `pocket-tts` isn't installed on a given machine). PR open, awaiting CodeRabbit + final hardware confirmation of the default-voice change before merge.
   - Future idea, not started: try a different Pocket TTS preset voice (or a cloned one) instead of the current default "alba" — Banmi wants to explore other voice options. **[proposed, 2026-08-14]**
4. iPhone bridge, Discord, Steam notifications, daily schedule — genuinely valuable but the most complex; sequence after the above, not before. **[confirmed, lower sequence]**

**Phase 2 — ambitious, deliberately deferred, not simultaneous with Phase 1:**
- Periodic local fine-tuning (LoRA-style) on Bruce's model, run offline on a schedule (e.g. weekly), trained on curated logs pulled from Bruce's own memory vault once that exists. This is real "active learning and development" rather than just memory lookup — but it depends on Phase 1's memory system existing first to supply good training data, and it's a project of its own (not something to build in parallel with everything else). Explicitly NOT live/real-time weight updates during conversation — that's a genuinely unsolved problem (catastrophic forgetting, heavier compute needs) and isn't being pursued. **[confirmed as phase 2, not started]**

**Local-first direction (ongoing philosophy, not a blocking requirement):**
- Banmi wants Bruce to run as close to fully local as possible, but wants to finish building out Bruce's full feature set first, then deliberately move existing cloud-dependent pieces toward local alternatives afterward — not mid-build.
- Current local/cloud status: Ollama/Qwen (brain) — local. Whisper (speech-to-text) — local. Kokoro (one of three voice options) — local. ElevenLabs and Edge-TTS (the other two voice options) — both cloud, despite "Edge" sounding local. Tavily (web search) — cloud.
- Later migration is genuinely easy for voice — Kokoro already exists and is already integrated, so dropping ElevenLabs/Edge-TTS later is low-cost.
- Web search is a real exception: "search the web" inherently requires reaching the actual internet somewhere, so it can never be fully offline. "Local" there would mean not depending on Tavily specifically (e.g. self-hosting something like SearXNG) rather than zero network access.
- Sharpen Bruce's `SYSTEM_PROMPT` so his tendency to push back / not blindly agree is more explicit, matching how Claude is now expected to operate in this project **[proposed, to-do — Banmi asked for this to be tracked, not yet implemented]**

## Security & Privacy — end-of-development hardening pass (added 2026-08-17)
Banmi's explicit reasoning, worth keeping front and center: the whole point of running Bruce locally instead of on a cloud assistant is privacy — Bruce knows his schedule, personal facts, preferences, and (per the item above) may eventually read his email and browse on his behalf. That's a lot of trust placed in one PC. He wants a dedicated security review as its own milestone once Bruce's feature set is otherwise "done" — not an ongoing background task, a deliberate pass — with the explicit goal of making Bruce "as impenetrable as possible." **[confirmed, sequenced for end of development, not started]**

Concrete things worth checking whenever this pass happens, so it's not just a vague "be more secure" gesture:
- What Bruce's local servers actually expose: `bruce.py` runs an HTTP server (port 8766), a WebSocket server (port 8765), and a stats server (port 9001). Confirm all three are bound to localhost only, not listening on the LAN/all interfaces — if they're not, anyone else on the same network could control Bruce or read what he's saying.
- `bruce_memory.json` (facts, preferences, session history) is currently stored as plaintext on disk. Fine under the "local-only, one PC" threat model; worth explicitly deciding whether that's still acceptable once Bruce has browser/email access and a bigger attack surface, or whether it should be encrypted at rest.
- Credential hygiene (already good practice, worth re-auditing not re-inventing): all live keys live in gitignored `bruce_secrets.py`, never hardcoded into `bruce.py` — confirm this is still true for any new integrations (email, browser automation) added later.
- Safety rails on the higher-risk new capabilities above: should Bruce require confirmation before sending an email or taking a consequential browser action (submitting a form, posting something, purchasing)? This is a design decision, not just a security patch — needs to be decided when those features are actually built, not deferred entirely to the end.
- General local-first posture ties directly into this: see "Local-first direction" above — every cloud dependency (ElevenLabs, Edge-TTS, Tavily) is also a place personal data leaves the PC, worth reassessing as part of the same pass, not just code-level exploitability.

## Pending Fixes
- TTS delay (~5 seconds with Kokoro)
- Monitor audio switch command not working
- Whisper/Vosk sometimes mishears what Banmi actually says (transcription accuracy) — flagged 2026-08-14 during the memory hardware test. Partially explained by several items below (interrupt crash, dead voice-interrupt paths, and the silence-bundling issue), all found and fixed/logged 2026-08-14. Some residual mishearing likely remains and isn't fully explained yet — revisit after the items below have had more real-world use.
- ~~Interrupt handling crash + two dead voice-interrupt code paths~~ **[DONE 2026-08-14, hardware-verified]** — CodeRabbit flagged a theoretical race on PR #4 (a stale `interrupt_flag` from the keyboard interrupt path silently swallowing Pocket TTS's next reply). That theory turned out not to be the actual bug — traced the real call graph and found `process_turn()` already force-clears the flag before every reply, which neutralizes that specific race. But Banmi's hardware test surfaced three *real*, separate bugs the theory missed entirely: (1) `bruce.py` had two different threads both calling `keyboard.wait(ACTIVATE_KEY)` at once (a dedicated `interrupt_listener()` thread, fully redundant with logic the main INSERT loop already had) — the `keyboard` library isn't safe for that, and one thread's internal hotkey cleanup racing the other's threw an unhandled `KeyError('insert')` that crashed the entire process, which is what looked like Bruce "freezing." Fixed by deleting the redundant thread. (2) `voice_interrupt_listener()` had a second mic-monitoring block that reused a `PyAudio` host object *after* the first block had already called `.terminate()` on it — throws every time, silently, so voice interrupts stopped working partway into any reply once the first monitoring loop ended. Fixed by removing the dead block (the first block's loop already covers Bruce's whole speaking duration on its own). (3) That same listener only ran while `conversation_mode` was True, but a hold-INSERT single-turn question deliberately sets `conversation_mode` False for its entire duration including the reply — so voice interrupt was silently impossible during any INSERT-triggered reply. Fixed by gating on `bruce_speaking` alone instead. All three confirmed fixed via repeated hardware interrupt testing (voice and keyboard, both during conversation mode and after an INSERT question) — no crash, no dead air. Merged into `bruce-pocket-tts` branch (commit `779e5b8`).
- **Post-interrupt audio still may be getting dropped at the very start of a new recording** — this was the *other* half of the original 2026-08-14 mishearing investigation, separate from the crash/dead-listener bugs above and not yet touched. `record_until_silence()` opens a brand-new mic stream only after an interrupt is fully processed, a gap of roughly 100-300ms during which anything Banmi is already saying could be lost. Needs its own retest now that the interrupt system actually works reliably — the original reproduction ("why did you bring up a YouTube video" → "me a YouTube video") happened back when interrupts were also crashing/failing outright, so it's worth confirming this specific gap is still real before investing in an architectural fix. **[proposed, not yet retested]**
- **`record_until_silence()`'s 1.5s silence cutoff bundles quick repeated speech into one turn** — found 2026-08-14: Banmi said "go to sleep" three times in a row trying to stop Bruce, and all three landed in a single "You:" transcription instead of three separate turns, because he never paused a full 1.5 seconds between attempts. Bruce wasn't ignoring him — it was still recording, waiting for silence. This likely contributes to the broader "Bruce misunderstands me" complaint beyond the interrupt-related bugs: any time Banmi's natural pauses between thoughts are under 1.5s, multiple separate things he says get glued into one turn. No fix implemented yet — options include shortening the threshold, or giving clearer real-time feedback that Bruce is still actively listening (ties into the existing "no clear listening state feedback" gap). **[proposed, not started]**
- HUD has no text input — voice-only right now, no way to type to Bruce instead of talking — flagged 2026-08-14
- Bruce says "Ready." out loud before the wake word system is actually ready — HUD's wake-readiness bar was only ~30% when the audio cue played, so it's telling Banmi he can talk before he reliably can. Likely the same root cause as the wake-word race condition fixed earlier (bruce.py's "Ready." fires once its own init finishes, not once the separate bruce_wake_1.py process has actually finished loading Vosk + its boot wait) — flagged 2026-08-14, not fixed yet
- ~~Bruce claimed it couldn't search the browser when asked~~ **[DONE 2026-08-14]** — root cause was two-fold: `SYSTEM_PROMPT`'s capability list never mentioned web search at all, and `is_search_query()` only matched sentences starting with an exact trigger phrase. Fixed: added search to the capability list, added conversational lead-in stripping to the fast path, and added `classify_search_intent()` as an LLM-based fallback for fully natural phrasing (only runs when a loose keyword hints at search, so ordinary chat never pays the extra latency — CodeRabbit caught that "know"/"information" were too broad and triggered on ordinary questions, narrowed after that). Hardware-verified working by Banmi, merged to `main` via PR #3.
- Memory is accumulating near-duplicate facts/preferences worded slightly differently across sessions (e.g. "Banmi prefers cold weather over hot weather" saved separately from "Banmi's preference for cold weather over hot weather") — exact-string dedup doesn't catch this. Not urgent, but will get noisier over time; worth a periodic consolidation/cleanup pass eventually — noted 2026-08-14
- ~~Bruce's personality feels non-existent in practice~~ **[DONE 2026-08-17, hardware-verified]** — rewrote `SYSTEM_PROMPT` with Banmi's requested traits (blunt, short-but-informative, sarcastic on human error, opinionated, challenges assumptions) plus example exchanges baked directly into the prompt (concrete examples steer tone better than descriptive adjectives alone). Combined with the model upgrade above, hardware test showed a dramatically more present personality ("The question is nonsensical... Specify the criteria," "I don't interrupt — I respond... Your call."). One real refinement needed and made same night: Bruce was applying "challenge assumptions" too broadly, stonewalling casual hypotheticals (e.g. a dinosaur-battle-royale question) by demanding the question be over-specified before answering. Fixed by adding an explicit line: challenge things that matter, answer casual hypotheticals with reasonable assumptions and a confident take, then offer to go deeper. Not yet retested after this specific refinement — worth confirming next session.
- Voice interrupt is too trigger-happy and slow to recover — `voice_interrupt_listener()` in `bruce.py` breaks Bruce out of speaking based on raw mic amplitude (`VOICE_THRESHOLD = 150` over ~3 consecutive chunks, ~100ms), not actual speech detection. Any loud noise (accidental bump, background sound) triggers it, not just Banmi talking, and recovering afterward takes long enough to disrupt the conversation. Flagged 2026-08-14. Needs real speech confirmation (e.g. requiring the "interrupting" audio to actually transcribe to something) instead of a bare volume threshold.
- ~~Debug lines still in CMD output~~ **[DONE]** — gated behind a `DEBUG_MODE` flag in `bruce.py` (default `False`); flip it to `True` to see raw Ollama request/response info again if troubleshooting is needed.
- ~~START_BRUCE.bat never launched bruce.py itself~~ **[DONE 2026-08-14]** — the post-Notepad-incident reconstruction only started the overlay and wake listener, so the wake word had nothing to actually signal. Added the missing `start "" python bruce.py` line.
- ~~Wake word race condition on boot~~ **[DONE 2026-08-14]** — `bruce_wake_1.py` had a fixed 12s wait before listening, but `bruce.py`'s slow imports (torch/Whisper/Kokoro) can take longer than that on a cold start, so the first "Bruce online" after launch would silently fail with "Could not reach Bruce." Made `signal_bruce()` retry for ~9 seconds instead of failing after one attempt.
