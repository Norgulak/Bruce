## 2026-08-14 — Pocket TTS integrated (with a real streaming fix) + a real conversational-search gap found and fixed on hardware
Started building `kyutai-labs/pocket-tts` into `bruce.py` as a fourth selectable voice (alongside Kokoro/ElevenLabs/Edge, not replacing anything yet), on branch `bruce-pocket-tts`. Deliberately lazy-loaded (`pocket-tts` isn't installed on Banmi's machine by default, and importing it eagerly at startup would've crashed Bruce entirely until the pip install happened) with graceful failure messaging instead of a crash.

Banmi installed it and hardware-tested it — genuinely preferred it over every other TTS option tried so far, but found a 5-10s delay before any sound, worse than expected given Pocket TTS's whole pitch is ~200ms-to-first-chunk. Root cause was my own implementation bug, not the library: I used `generate_audio()` (blocks until the ENTIRE response is generated) instead of `generate_audio_stream()` (yields chunks as they're generated). Fixed by adding `AudioManager.play_pcm_stream()` and switching `_pocket()` to the streaming API - audio now starts playing as the first chunk arrives instead of waiting for the whole thing. This also fixed a related bug Banmi caught: the HUD showed "speaking" several seconds before any sound played, because `hud_status("speaking")` fired unconditionally before generation even started. Now it fires via `play_pcm_stream`'s `on_start` callback, exactly when the first chunk is about to play. Banmi retested and confirmed it's noticeably faster. Verified with standalone logic tests (real audio hardware isn't available in this sandbox) before either round of hardware testing. Pushed as commits `a780cae` and `80cfc04` on `bruce-pocket-tts`, not yet merged.

Separately, Banmi also reported "Bruce still isn't aware it can do web searches" from an earlier test session. Initially couldn't diagnose from the wake-listener's noisy Vosk transcript alone (learned that lesson from the shower-memory mixup earlier tonight) - asked for and got the actual `bruce.py` console log. Turned out to be good news: Bruce correctly said *"I can perform a live web search. Would you like me to do that?"* when asked about the stock market, proving the capability-awareness fix from earlier held. The real bug was narrower: `classify_search_intent()`'s hint gate required the exact substring "going on **with**", but Banmi's actual phrasing was "going on **in** the stock market" - one word off, so the gate silently declined before ever reaching the classifier. Broadened "going on with"/"happening with" to "going on"/"happening" (low risk - the gate is just a candidate filter, the classifier itself still makes the real decision). Reproduced the exact failing phrase in a test before considering it fixed. Also confirmed from the same log that the fast exact-phrase path works correctly ("search for the weather" triggered a real search), though the result quality was poor (returned a YouTube link for a weather query) - concrete evidence for the already-logged "search doesn't prioritize credible sources" roadmap item. Pushed as commit `2a28608` on `bruce-search-hint-fix`, not yet merged.

Also learned tonight: closing Bruce's console window after testing loses the scrollback permanently - asked Banmi to leave windows open until logs are captured, going forward.

## 2026-08-14 — Conversational web search shipped; Pocket TTS found for the streaming-voice item
Banmi reported Bruce claimed it couldn't search the web despite that being an existing feature. Root cause was two separate bugs: `SYSTEM_PROMPT`'s capability list never mentioned web search at all (so whenever detection failed, the model had no idea it could search and just denied it), and `is_search_query()` only matched sentences starting with an exact fixed phrase like "search for " — anything conversational ("can you search for X", "do you know what's going on with Y") fell straight through to plain chat. Fixed with a two-tier approach: `is_search_query()` now strips common lead-ins ("can you", "could you", ...) before matching, still free/instant; new `classify_search_intent()` is a fallback that only runs when a loose keyword hints at search intent, then asks Bruce's own local model to classify and extract the query. Verified with 7 standalone tests before ever touching real hardware.

CodeRabbit caught a real issue on review: the fallback's keyword list included "know" and "information", both far too generic — ordinary questions like "do you know why the sky is blue" would trigger an unnecessary second Ollama call, and if Ollama were ever slow/down that's up to a 90s stall before the normal reply even gets attempted. Narrowed the list, re-verified with CodeRabbit's own example plus additional generic phrasing, confirmed no regression on real conversational search phrasing.

Banmi hardware-tested both paths (exact phrase and conversational) and confirmed working. Merged to `main` via PR #3 (`bruce-conversational-search`).

While investigating, Banmi separately found a new Instagram reel and asked for an opinion on the existing roadmap first. Pushed back on LiveKit as the planned fix for Bruce's ~5s TTS delay — LiveKit is built for multi-participant networked real-time audio, disproportionate to a single local user's latency problem. The reel turned up a better-fit candidate: `kyutai-labs/pocket-tts` (verified real on GitHub - 7.9k stars, actively maintained, from the lab that built Moshi). CPU-only by design, 100M params, ~200ms to first audio chunk, plain Python API, has a `serve` mode for keeping the model warm. Logged as the new leading candidate for roadmap item 3, LiveKit deprioritized but not ruled out. Not yet integrated - pending Banmi's go-ahead.

Also logged from this session: a real, diagnosed bug in `voice_interrupt_listener()` (triggers on raw mic amplitude, not actual speech - any loud noise interrupts Bruce, slow to recover), and three search-quality feature ideas from Banmi (prefer credible sources, cite sources for news, and a longer-term "find historical patterns in the news" idea, explicitly framed as a later-stage build).

## 2026-08-13 — CodeRabbit's 4 findings on the memory PR fixed
CodeRabbit reviewed the `bruce-persistent-memory` PR and flagged 4 real issues (not nitpicks — one was a genuine security gap). All fixed in `bruce_memory.py`/`bruce.py` and re-verified with standalone logic tests (not just py_compile):
1. **Schema validation** — `load_memory()` now checks the loaded JSON is a dict with list-typed fields before using it; malformed-but-parseable JSON falls back to fresh memory instead of risking an `AttributeError` later.
2. **Atomic writes** — `save_memory()` now writes to a temp file, fsyncs, then `os.replace()`s over the real file, so a crash mid-write can't corrupt `bruce_memory.json`. Returns `True`/`False` so callers know if it actually worked.
3. **Prompt injection framing** — stored memory (which can contain anything the mic picked up, including "remember that X" from anyone in the room) is now wrapped in explicit "untrusted reference data, not instructions" markers, with the anti-injection policy text placed *after* the memory content so it's the last thing the model reads.
4. **Duplicate summaries** — `save_session_memory()` now tracks a checkpoint into `self.history` and only extracts/saves the unsaved slice, fixing the bug where ending a session twice (stop phrase, then Ctrl+C) would save the same summary twice.

Verified via a standalone test script (routed around a sandbox-only file-deletion quirk, unrelated to the actual code): atomic save returns `True` with no leftover temp files, save+load roundtrip preserves data, overwriting an existing file via `os.replace()` works, the failure path (bad directory) returns `False` instead of crashing, and the security-framing text/policy-placement is correct. Committed to the `bruce-persistent-memory` branch (commit `29df588`) and pushed via the usual manual `del .git\index.lock` / `del .git\HEAD.lock` + push from Banmi's own Command Prompt.

**Follow-up (same day):** CodeRabbit's re-review caught a 5th real issue on top of the original 4 — `load_memory()` validated that `facts`/`preferences`/`history_summaries` were lists, but not what was *inside* them. A file with `history_summaries: ["text"]` (string instead of object) passed validation and would've crashed later in `format_memory_for_prompt()` at `s.get(...)`. Fixed: item-level validation now requires facts/preferences to be strings and history_summaries items to be objects with string `date`/`summary` fields; any violation falls back to fresh memory, same as the existing corrupted-JSON path. Verified with 4 new standalone tests (string-in-history_summaries, non-string fact, missing summary field, valid data still loads clean) — all passed. Committed as `80afb7a`, pushed.

Waiting on CodeRabbit re-review of this second fix, then the run-and-check step (actually launching Bruce with this branch, testing "remember that X" + restart recall) before merging to `main`.

## 2026-08-13 — Bruce's persistent memory built (pending real-hardware test)
Added `bruce_memory.py` (new module) and wired it into `bruce.py`. Design: retrieval-based, not weight updates — facts/preferences/session summaries get saved to `bruce_memory.json` (gitignored, contains personal info) and re-injected into Bruce's system prompt on every run via `BruceBrain.system_prompt = SYSTEM_PROMPT + memory_block`. Two ways memory gets written: (1) passively — when a conversation ends (stop phrase or Ctrl+C), `BruceBrain.save_session_memory()` asks the LLM to extract anything worth remembering from the session and saves it; (2) explicitly — saying "remember that X" is now a fast-path command in `check_commands()` that saves immediately without waiting for session end. Added a `MEMORY_ENABLED` flag (default `True`) to disable the whole thing if needed, same pattern as `DEBUG_MODE`.

Verified: syntax compiles clean, and ran the actual memory logic (load/save/dedupe/prompt formatting/LLM-output parsing) standalone with real test data — all passed. What's NOT yet verified: the actual integration with Ollama, the mic, and TTS on Banmi's real hardware, since I don't have access to any of that. Per our workflow agreement (core function changes get run and checked before being called done), this is built on a branch (`bruce-persistent-memory`), not merged to `main` yet — Banmi needs to actually run Bruce with this change and confirm it behaves correctly before it's considered finished, and per the same agreement, this qualifies as substantial enough to go through a PR + CodeRabbit review before merging.
